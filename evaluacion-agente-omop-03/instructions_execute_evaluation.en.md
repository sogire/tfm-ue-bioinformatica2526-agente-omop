# OMOP Agent Execution and Evaluation Guide

This document describes the official, unified evaluation workflow for benchmarking queries generated by the OMOP Text-to-SQL agent (`omop_03_concepts_and_sql`) against the *Gold Standard* defined in the evaluation YAML files under [evaluation/gold_standard/](evaluation/gold_standard/), generated according to the guidelines in [instructions_build_gold_standard.en.md](instructions_build_gold_standard.en.md) ([Spanish version](instructions_build_gold_standard.md)).

> [!NOTE]
> **Modularity and New SQL Query Sources:**
> The current evaluated query source is `querylibrary` (from the OHDSI Query Library). The system is designed to be multi-source: in the future, new SQL query sources (e.g., `mimic`, `custom_ehr`, etc.) can be added under `evaluation/sources/<new_source>/`, generating their gold standard in `evaluation/gold_standard/<new_source>/` and storing execution results in `evaluation/results/<new_source>/`. All scripts support the `--source` parameter (defaulting to `querylibrary`).

All evaluations and downstream analyses are executed in a standardized, automated manner using the scripts organized under the **[`scripts/execute_evaluation/`](scripts/execute_evaluation/)** directory.

---

## Directory Structure and Scripts

* **Gold Standard (Test Cases):** `evaluation/gold_standard/<source>/` (default: `evaluation/gold_standard/querylibrary/` with 201 cases).
* **Evaluation Results:** `evaluation/results/<source>/` (default: `evaluation/results/querylibrary/` with per-case YAML files).
* **Forensic Sessions:** `evaluation/results/<source>/sessions/` (JSON files containing the complete ADK session trace).
* **Consolidated Reports:** `evaluation/results/<source>_analisis_yyyymmddhhmm.xlsx`.
* **Environment Dependencies:** [`requirements.txt`](requirements.txt) (`pip install -r requirements.txt`).
* **Execution and Analysis Scripts:** `scripts/execute_evaluation/`
  * [`run_query_evaluation.py`](scripts/execute_evaluation/run_query_evaluation.py): Test runner against the agent on Google Cloud Run. Supports `--source <source>` (default `querylibrary`).
  * [`analyze_evaluation_results.py`](scripts/execute_evaluation/analyze_evaluation_results.py): Results consolidator and Excel analyzer (`evaluation/results/<source>_analisis_yyyymmddhhmm.xlsx`). Supports `--source <source>` (or `all`).

## 1. Automated Execution with `run_query_evaluation.py`

The [`run_query_evaluation.py`](scripts/execute_evaluation/run_query_evaluation.py) script transparently manages the session lifecycle with the agent on Google Cloud Run, sending the prompt with an explicit SQL directive, resolving multi-turn terminological disambiguation dialogues, extracting the SQL query, and calculating both quantitative and qualitative metrics.

### A. Single Case Evaluation
To evaluate a single test case (for example, `C01` from `querylibrary`):
```bash
# Default source (querylibrary)
python3 scripts/execute_evaluation/run_query_evaluation.py C01

# Explicitly specifying the source
python3 scripts/execute_evaluation/run_query_evaluation.py --source querylibrary C01
```

### B. Range Evaluation (Batch)
To continuously evaluate a sequential block of cases (for example, from case `C01` to `C10`):
```bash
python3 scripts/execute_evaluation/run_query_evaluation.py --range C01-C10
```

### C. Specific Case List Evaluation
To evaluate specific non-sequential cases:
```bash
python3 scripts/execute_evaluation/run_query_evaluation.py C01 C03 C06 C10
```

### D. Full Collection Evaluation
To automatically evaluate all YAML files present in `evaluation/gold_standard/<source>/`:
```bash
python3 scripts/execute_evaluation/run_query_evaluation.py --all
```

> [!TIP]
> **Optional Parameters:**
> * `--source <name>`, `-s`: Query source identifier or type (default: `querylibrary`).
> * `--delay <seconds>`, `-d`: Configures the wait time in seconds between consecutive queries to the agent (default `1.5` s).
> * `--base-dir <path>`: Manually specifies the project root if executed from another working directory (default: auto-detected).
> * `-h` / `--help`: Displays help and available command-line options.

## 2. Evaluation Metrics and Output Format

Each evaluation analyzes the agent's behavior using two quantitative metrics, a third multi-line qualitative metric, and a technical connectivity indicator:

### Metric 1: `validez_sintactica_y_estructural` (0.00 to 1.00)
* **Nature:** Continuous quantitative metric on a `[0.00, 1.00]` scale.
* **Objective:** Jointly evaluate the technical executability and validity of the SQL query alongside its logical and structural fidelity compared to the standard reference query (`sql_base_gold_standard`).
* **Calculation and Criteria Weighting:**
  $$\text{validez\_sintactica\_y\_estructural} = \text{Criterion 1.1} + \text{Criterion 1.2}$$
  * **Criterion 1.1 — Execution and Technical Validity (maximum 0.10 points):**
    * **0.10:** If the generated query is syntactically valid, structured for Google BigQuery OMOP CDM 5.4, and either validated successfully by the agent's internal tool (`validate_omop_sql`) or emitted as an executable `SELECT` statement.
    * **0.00:** If the query has syntax errors, fails to compile against the catalog, or if the agent failed to formulate executable SQL.
  * **Criterion 1.2 — Degree of SQL Similarity vs. Gold Standard (maximum 0.90 points):**
    * **Scoring:** Evaluated by **Gemini as an *LLM-as-a-judge*** comparing the agent's SQL query against `sql_base_gold_standard`.
    * **Similarity criteria:** Business logic, OMOP model tables used, filtering conditions (`WHERE`), joins (`JOIN`), aggregations (`GROUP BY`), and alignment with clinical intent.
    * **Projection flexibility:** Field aliases or column names in the `SELECT` clause do not need to be named identically, provided the query answers the same clinical need and selects the relevant information.
    * **0.00:** If the agent did not generate an executable SQL query (Criterion 1.1 = 0.00) or if the generated query is completely erroneous with respect to the clinical need.

### Metric 2: `precision_terminologica_vocabulario` (0.00 to 1.00)
* **Nature:** Continuous quantitative metric.
* **Objective:** Evaluate fidelity in concept identification compared to those defined in `concept_ids_gold_standard`.
* **Calculation:** Jaccard index between the concepts used by the agent ($C_{\text{agent}}$) and those required by the gold standard ($C_{\text{gold}}$):
  $$\text{Jaccard} = \frac{|C_{\text{agent}} \cap C_{\text{gold}}|}{|C_{\text{agent}} \cup C_{\text{gold}}|}$$
  *(In exploratory queries where the gold standard does not fix mandatory numeric concepts, the assigned value is 1.00).*

### Metric 3: `evaluacion_cualitativa` (YAML Multi-line Block)
* **Nature:** Descriptive qualitative metric formatted as a multi-line text block (`|-`).
* **Objective:** Provide a structured semantic, clinical, and technical analysis of the model's behavior on the evaluated case.
* **Evaluated Content:**
  * **Conversational resolution and technical execution:** Indicates whether the agent generated the query directly in a single turn or required additional dialogue/disambiguation turns, along with the technical score obtained (Criterion 1.1: 0.10 pts).
  * **SQL similarity evaluated by Gemini:** Technical and clinical summary issued by Gemini justifying the score awarded out of 0.90 points (Criterion 1.2).
  * **OMOP tables and model:** Documents the CDM tables involved in the generated query (e.g., `concept`, `concept_relationship`, `condition_occurrence`, `measurement`, `specimen`).
  * **Clinical and terminological alignment:** Explains the relevance of the mapped concepts with respect to the original medical intent.
  * **Abstention or failure diagnosis:** In cases where no SQL is formulated (e.g., lack of SNOMED–MedDRA cross-mapping or distinction between pathogenic organism and clinical event), documents the medical justification provided by the agent.

### Technical Indicator: `check_conexion`
* **Objective:** Record the HTTP/SSE communication status with the agent's Cloud Run service.
* **Values:**
  * `true`: Connection established successfully and ADK session executed properly.
  * `Fallo de conexión: <detail>`: In case of a timeout, HTTP error (500, 503), or remote service outage.

### Resulting YAML File Format
Each evaluated case generates its corresponding file in [evaluation/results/<source>/](evaluation/results/querylibrary/) (default: `evaluation/results/querylibrary/`) with clean multi-line formatting and strict syntactic validation:

```yaml
id_evaluacion: querylibrary_C03
session_id: "09c86a27-e43c-423c-a22f-1962a3eece7d"
session_file: "sessions/C03.json"
turnos_ejecutados: 1
sql_generada_agente: |-
  SELECT c1.concept_id AS source_concept_id,
         c1.concept_name AS source_concept_name,
         c1.vocabulary_id AS source_vocabulary_id,
         cr.relationship_id,
         r.relationship_name,
         c2.concept_id AS target_concept_id,
         c2.concept_name AS target_concept_name,
         c2.vocabulary_id AS target_vocabulary_id,
         c2.domain_id AS target_domain_id
  FROM `concept` AS c1
  JOIN `concept_relationship` AS cr ON c1.concept_id = cr.concept_id_1
  JOIN `relationship` AS r ON cr.relationship_id = r.relationship_id
  JOIN `concept` AS c2 ON cr.concept_id_2 = c2.concept_id
  WHERE c1.concept_id = 312327
  ORDER BY r.relationship_name,
           c2.concept_name;
concept_ids_identificados_agente:
- 312327
metricas_evaluacion:
  validez_sintactica_y_estructural: 0.75
  precision_terminologica_vocabulario: 1.0
  detalle_validez_sintactica:
    criterio_1_1_ejecucion: 0.10
    criterio_1_2_similitud_sql_gemini: 0.65
    justificacion_gemini: |-
      La consulta generada implementa adecuadamente la unión entre concept, concept_relationship y relationship para encontrar relaciones del concepto 312327, pero omite filtrar por c.invalid_reason IS NULL.
  metricas_por_turno:
    turno_1:
      validez_sintactica_y_estructural: 0.75
      precision_terminologica_vocabulario: 1.0
      question_improvement: ""
evaluacion_cualitativa: |-
  Consulta SQL ejecutable (0.10 pts) sobre tabla(s) concept, concept_relationship, relationship generada en el Turno 1 tras la confirmación de los conceptos iniciales ofrecidos por el agente.
  Similitud SQL evaluada por Gemini (0.65/0.90 pts): La consulta generada implementa adecuadamente la unión entre concept, concept_relationship y relationship para encontrar relaciones del concepto 312327, pero omite filtrar por c.invalid_reason IS NULL.
  Precisión terminológica óptima: identificó y utilizó todos los conceptos requeridos ([312327]).
check_conexion: true
```

> [!NOTE]
> **Multi-Turn Structure and Detailed Metrics:**
> * `session_id` / `session_file`: Unique identifier and relative path to the forensic audit JSON dump downloaded directly from the Google ADK session endpoint on Cloud Run (`/apps/{appName}/users/{userId}/sessions/{sessionId}`) and preserved in `evaluation/results/<source>/sessions/<case>.json`.
> * `turnos_ejecutados`: Number of turns required by the agent (1 if Syntactic and Structural Validity exceeded 0.80 in the first round; 2 if it exceeded 0.80 after the first feedback round; or 3 if all 3 turns were required).
> * `metricas_por_turno`: Granular breakdown reflecting metric evolution across each turn (`turno_1`, `turno_2`, `turno_3`).
> * `question_improvement`: Contains the enriched prompt used in subsequent turns (Turns 2 and 3) incorporating the `justificacion_gemini` feedback from the LLM judge in the previous turn to guide the agent toward the optimal query. In `turno_1`, it remains empty (`""`).

## 3. Architecture and Internal Operation of `run_query_evaluation.py`

The [`run_query_evaluation.py`](scripts/execute_evaluation/run_query_evaluation.py) script encapsulates the following specialized functions:

1. **Remote Session Management with ADK / Cloud Run (`create_agent_session`, `send_message_sse`):**
   * Opens a new session (`POST /apps/{APP_NAME}/users/{USER_ID}/sessions/{SESSION_ID}`).
   * Sends the natural language question along with the explicit directive requiring a BigQuery OMOP 5.4 SQL query via Server-Sent Events (`POST .../run_sse`).
2. **Multi-Turn Feedback Loop Guided by an LLM Judge (`justificacion_gemini`):**
   * **Early Stopping Criterion:** Whenever the **Syntactic and Structural Validity** of a turn exceeds `0.80` (`validez_sintactica_y_estructural > 0.80`), no subsequent turn is executed and the evaluation concludes successfully on the current turn.
   * **Turn 1 (Clinical Question and Initial Evaluation):** Sends the original question directly requesting executable SQL formulation for BigQuery OMOP 5.4. If the agent proposes initial candidate concepts for validation, the evaluator's immediate confirmation of those concepts forms an integral part of **Turn 1**. The obtained response (generated SQL or textual response) is evaluated by the Gemini LLM judge (`judge_sql_similarity_with_gemini`), yielding the continuous score (`criterio_1_2_similitud_sql_gemini`) and detailed critique (`justificacion_gemini`). If Syntactic and Structural Validity exceeds 0.80 (> 0.80), the interaction concludes successfully with `turnos_ejecutados = 1` without executing the next turn.
   * **Turn 2 (LLM Judge-Guided Improvement):** If Turn 1 Syntactic and Structural Validity does not exceed 0.80 (validity <= 0.80) or the agent did not formulate SQL, the evaluator builds an enriched prompt (`question_improvement`) injecting the full technical and clinical feedback from Turn 1's `justificacion_gemini` (pointing out missing tables, `WHERE` filters, `JOIN` clauses, and domains). The agent processes this feedback within the same session and generates a corrected version, which is re-evaluated by Gemini. If Syntactic and Structural Validity exceeds 0.80 (> 0.80) on this turn, it concludes with `turnos_ejecutados = 2` without executing Turn 3.
   * **Turn 3 (Final LLM Judge-Guided Optimization):** If Syntactic and Structural Validity still does not exceed 0.80 (validity <= 0.80) after Turn 2, the evaluator injects the new `justificacion_gemini` returned by the LLM judge in Turn 2 into the follow-up instruction (`question_improvement`), requiring the agent to resolve the noted issues and emit the final optimal `SELECT` SQL statement for BigQuery OMOP CDM 5.4. The evaluator concludes with `turnos_ejecutados = 3` and consolidates the query and metrics from the best executed turn.
3. **SQL Extraction and Validation (`extract_sql_from_events`):**
   * Inspects tool calls and responses (`validate_omop_sql`, `search_omop_official_concepts`) within the SSE events.
   * Extracts the final query and the BigQuery validation verdict.
4. **Metric Calculation and Safe Serialization:**
   * Records metrics for each executed turn and includes the `question_improvement` field.
   * Uses a custom `LiteralStr` class with a dedicated PyYAML representer to ensure both SQL code and qualitative text are serialized with the `|-` literal multi-line indicator, eliminating redundant escape characters.
5. **Forensic Auditing and ADK Session Persistence:**
   * Automatically downloads the complete session state via `GET /apps/{appName}/users/{userId}/sessions/{sessionId}` and saves it in `evaluation/results/<source>/sessions/<case>.json`.
   * The JSON session contains the full forensic trace: events, tool calls and responses, model reasoning, token consumption (`usageMetadata`), and timestamps.
6. **Resilience Against Quota Exhaustion and Unresponsiveness (`request_with_retry`):**
   * If the OMOP agent experiences quota exhaustion (HTTP 429 / `RESOURCE_EXHAUSTED` / rate limit), service overload (HTTP 500/502/503/504), or communication interruption (*timeout*, connection failure, or empty SSE response), the evaluator catches the event, immediately prints the active `id_evaluacion` to the console, and performs a preventive **2-minute (120-second)** pause before retrying the operation (up to 5 retries).

## 4. Analysis and Consolidation in Excel (`analyze_evaluation_results.py`)

As the final step in the evaluation workflow, once the user approves processing and consolidating the results obtained from executions against the agent, the [`analyze_evaluation_results.py`](scripts/execute_evaluation/analyze_evaluation_results.py) script is executed.

### Purpose and Data Flow
1. **Test Case Extraction (`test`):** Recursively reads the YAML files under [evaluation/gold_standard/<source>/](evaluation/gold_standard/) and builds the `test` DataFrame with the fields:
   * `source`
   * `id_evaluacion`
   * `nivel_complejidad`
   * `domain_main`
   * `domain_others`
   * `pregunta_lenguaje_natural`
   * `sql_base_gold_standard`
2. **Agent Results Extraction (`result`):** Recursively reads the YAML files under [evaluation/results/<source>/](evaluation/results/) and builds the `result` DataFrame with the fields:
   * `id_evaluacion`
   * `session_id`
   * `check_conexion`
   * `turnos_ejecutados`
   * `validez_sintactica_y_estructural`
   * `criterio_1_1_ejecucion`
   * `criterio_1_2_similitud_sql_gemini`
   * `precision_terminologica_vocabulario`
   * `turno_1_validez_sintactica_y_estructural`
   * `turno_1_precision_terminologica_vocabulario`
   * `turno_1_question_improvement`
   * `turno_2_validez_sintactica_y_estructural`
   * `turno_2_precision_terminologica_vocabulario`
   * `turno_2_question_improvement`
   * `turno_3_validez_sintactica_y_estructural`
   * `turno_3_precision_terminologica_vocabulario`
   * `turno_3_question_improvement`
   * `evaluacion_cualitativa`
   * `evaluacion_llm_juez`
   * `sql_generada_agente`
3. **Cross-Referencing and Consolidation:** Merges both DataFrames on `id_evaluacion` and sorts cases naturally by their identifier. Includes 27 logically ordered columns with `source` in the first position:
   * Metadata: `source`, `id_evaluacion`, `session_id`, `session_file`, `nivel_complejidad`, `domain_main`, `domain_others`, `pregunta_lenguaje_natural`
   * Execution and overall metrics: `check_conexion`, `turnos_ejecutados`, `validez_sintactica_y_estructural`, `criterio_1_1_ejecucion`, `criterio_1_2_similitud_sql_gemini`, `precision_terminologica_vocabulario`
   * Per-turn breakdown: `turno_1_validez_sintactica_y_estructural`, `turno_1_precision_terminologica_vocabulario`, `turno_1_question_improvement`, `turno_2_validez_sintactica_y_estructural`, `turno_2_precision_terminologica_vocabulario`, `turno_2_question_improvement`, `turno_3_validez_sintactica_y_estructural`, `turno_3_precision_terminologica_vocabulario`, `turno_3_question_improvement`
   * Queries and analysis: `evaluacion_cualitativa`, `evaluacion_llm_juez`, `sql_base_gold_standard`, `sql_generada_agente`.
4. **Excel Export:** Generates an `.xlsx` workbook under the `evaluation/results/` directory featuring professional styling, monospaced typography for SQL columns (`Consolas`), styled headers, auto-adjusted column widths, and multi-line alignment:
   ```text
   evaluation/results/<source>_analisis_yyyymmddhhmm.xlsx
   ```
   where `<source>` is the evaluated source (e.g., `querylibrary`) and `yyyymmddhhmm` corresponds to the exact year, month, day, hour, and minute of execution.

### Execution Command
```bash
# Default source (querylibrary)
python3 scripts/execute_evaluation/analyze_evaluation_results.py

# Analyze a specific source or all ('all')
python3 scripts/execute_evaluation/analyze_evaluation_results.py --source querylibrary
python3 scripts/execute_evaluation/analyze_evaluation_results.py --source all
```

> [!TIP]
> **Optional Analysis Parameters:**
> * `--source <source>`, `-s`: Identifier of the source to analyze (default: `querylibrary`, or `all` for all sources).
> * `--eval-dir <path>`, `-e`: Base directory for test files (default: `evaluation/gold_standard/<source>`).
> * `--results-dir <path>`, `-r`: Base directory for result files (default: `evaluation/results/<source>`).
> * `--output <name.xlsx>`, `-o`: Specify a custom filename or path for the Excel file (default: `evaluation/results/<source>_analisis_yyyymmddhhmm.xlsx`).
> * `--base-dir <path>`, `-b`: Project root directory (default: auto-detected).
